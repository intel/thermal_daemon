# thermald Developer and Contributor Guide

This document explains *what thermald actually does at runtime* and *where in the
source it does it*. It is aimed at new developers and contributors, and at anyone
debugging a report of the form "thermald did something to my machine and I don't
know why".

> reading the thermald sources at commit `d5bc616`. It is a description of the
> code, not a specification of it. Where this document and the source disagree,

## 1. What thermald is

thermald is a userspace daemon that keeps a platform from overheating, and — just
as importantly — keeps it from being throttled *more* than necessary. It does
this by reading temperature sensors and writing to kernel cooling interfaces
(RAPL power limits, cpufreq max frequency, powerclamp idle injection, fans,
backlight, ...).

Two things follow from being in userspace:

1. **thermald does not replace the kernel thermal core.** By default it runs in
   `COMPLEMENTRY` mode: the kernel keeps doing whatever its own trip points and
   governors say, and thermald adds control on top. In `EXCLUSIVE` mode
   (`--exclusive-control`, and implicitly in adaptive mode) thermald switches
   every thermal zone's policy to `user_space` and takes over.
2. **thermald is slow by design.** The control loop runs every few seconds. It
   is not, and cannot be, a substitute for hardware protections such as PROCHOT
   or thermal shutdown. Its job is to act *before* the hardware has to.

thermald's other job, less obvious from the name, is **applying the platform's
DPTF/DTT thermal tables** on Intel platforms. Those tables live in ACPI firmware
and describe the OEM's intended thermal and power behaviour. That is what
`--adaptive` is about, and it is covered in [section 7](#7-the-adaptive-engine---adaptive).

## 2. The mental model

Five object types, and everything else is plumbing:

| Object | Class | What it is |
| --- | --- | --- |
| **Sensor** | `cthd_sensor` ([src/thd_sensor.h](src/thd_sensor.h)) | Something you can read a temperature from. Usually a sysfs file. |
| **Zone** | `cthd_zone` ([src/thd_zone.h](src/thd_zone.h)) | A group of sensors plus a list of trip points. The thing that gets "checked". |
| **Trip point** | `cthd_trip_point` ([src/thd_trip_point.h](src/thd_trip_point.h)) | "At temperature T, act on these cooling devices." |
| **Cooling device** | `cthd_cdev` ([src/thd_cdev.h](src/thd_cdev.h)) | Something you can write to, to reduce heat. Has a state between `min_state` (no cooling) and `max_state` (maximum cooling). |
| **Engine** | `cthd_engine` ([src/thd_engine.h](src/thd_engine.h)) | Owns all of the above, runs the control loop. |

The single most important convention to internalise:

> **`min_state` means "no cooling applied". `max_state` means "maximum cooling
> applied". Numerically, `max_state` may be *lower* than `min_state`.**

For a fan, `min_state=0` (off) and `max_state=N` (full speed) — the numbers go
up as cooling increases. For a RAPL power limit, "no cooling" is the *highest*
allowed wattage and "maximum cooling" is the *lowest* wattage, so
`min_state=45000000` and `max_state=15000000`. This "inverted range" case is
handled explicitly all over [src/thd_cdev.cpp](src/thd_cdev.cpp) — see
`in_min_state()`, `in_max_state()`, `cmp_current_state()`,
`thd_clamp_state_min()`, `thd_clamp_state_max()`. When you touch cooling device
code, always ask yourself "does this still hold if max < min?".

Temperatures are in **millidegrees Celsius** everywhere internally.

## 3. Startup

Entry point is `main()` in [src/main.cpp](src/main.cpp) (Android has its own in
[src/android_main.cpp](src/android_main.cpp)).

```
main()
 ├─ parse options (GOption)
 ├─ must be root; create TDRUNDIR (/var/run/thermald) and TDCONFDIR (/etc/thermald)
 ├─ take PID lock on TDRUNDIR/thermald.pid  → refuse to start a second instance
 ├─ install the g_log handler (all logging goes through thd_logger())
 ├─ create GMainLoop, optionally start the D-Bus server (--dbus-enable)
 ├─ daemonize (unless --no-daemon or --systemd)
 ├─ if (--adaptive)  thd_engine_create_adaptive_engine()
 │       └─ on failure: fall back to thd_engine_create_default_engine()
 │  else             thd_engine_create_default_engine()
 └─ g_main_loop_run()          ← main thread now only serves D-Bus
```

Note the split: after startup the **GMainLoop thread does nothing but D-Bus**.
All thermal work happens on a separate pthread created in
`cthd_engine::thd_engine_start()`. Communication from D-Bus (or from signals)
into that thread goes through a pipe — `send_message()` /
`proc_message()`. If you add a D-Bus method that mutates engine state, either go
through a message or take `thd_engine_lock()`.

Engine creation is a three-step dance, the same for both engines:

1. `thd_engine_init()` — CPU model check, then discover sensors, cooling devices
   and zones, in that order (`read_thermal_sensors()`, `read_cooling_devices()`,
   `read_thermal_zones()`). Any failure here is fatal.
2. `thd_engine_start()` — set up the poll fds, decide polling vs uevent, spawn
   the engine thread, read the user preference, take over control if exclusive.
3. the thread runs `thd_engine_thread()` forever.

### Exit codes

| Code | Meaning |
| --- | --- |
| 0 | clean exit (also used when adaptive mode decides this platform is unsupported) |
| 1 | failure |
| 2 | `EXIT_UNSUPPORTED` — engine init returned `THD_ERROR`, e.g. unsupported CPU with no usable config |

[data/thermald.service.in](data/thermald.service.in) sets
`SuccessExitStatus=2` so that an unsupported platform is not reported as a
service failure, and `Restart=on-failure` — which matters for the adaptive
fallback path described in [section 7.6](#76-when-adaptive-mode-gives-up).

## 4. Discovery: how thermald decides what to control

This is the part users most often find surprising, because thermald invents
zones and trip points that do not exist in `/sys/class/thermal`.

`cthd_engine_default` ([src/thd_engine_default.cpp](src/thd_engine_default.cpp)) does the following.

**Sensors** (`read_thermal_sensors()`):

* every `/sys/class/thermal/thermal_zoneN` becomes a sensor;
* `pkg-temp-0`, `x86_pkg_temp` and `soc_dts0` are force-marked async-capable
  (they can notify via uevent, so polling is not required);
* every `tempN_input` under a `coretemp` platform/hwmon device becomes a sensor;
* sensors from `thermal-conf.xml` are added, or existing ones have their path
  and async capability overridden;
* virtual sensors (a linear combination of other sensors, `cthd_sensor_virtual`)
  are created from config.

**Cooling devices** (`read_cooling_devices()`), in priority order:

* every `/sys/class/thermal/cooling_deviceN`;
* `rapl_controller` (powercap MSR interface, aliased `B0D4`);
* `rapl_controller_mmio` (powercap MMIO interface) — preferred over MSR when
  available, at which point the MSR device loses the `B0D4` alias and, in
  adaptive mode, is pushed to 200 W so it stops interfering;
* `intel_pstate` (max frequency percentage);
* `intel_powerclamp` and `LCD` (statically defined in `cpu_def_cooling_devices[]`);
* `cpufreq`, `rapl_controller_dram`;
* `spel_controller_<domain>_pl<N>` for Qualcomm SPEL powercap domains;
* `LCD` backlight if not already present;
* anything defined in `thermal-conf.xml`.

**Zones** (`read_thermal_zones()`):

* every `/sys/class/thermal/thermal_zoneN` becomes a zone (inactive unless
  something binds a cooling device to it);
* `add_int340x_processor_dev()` — if an INT340X processor thermal device
  (`B0D4`/`B0DB`/`TCPU`) exists with a passive trip above 90 °C, it becomes *the*
  CPU zone, and `rapl_controller`, `intel_pstate`, `intel_powerclamp` and
  `Processor` are bound to its passive trip. If ACPI `_CRT` from `acpitz` is
  within 5 °C of that passive trip, the passive trip is lowered to
  `critical - 15 °C` so that Linux does not shut the box down before thermald
  can act;
* otherwise a synthetic zone named **`cpu`** (`cthd_zone_cpu`,
  [src/thd_zone_cpu.cpp](src/thd_zone_cpu.cpp)) is created from coretemp/hwmon.
  Its trip points are *computed*, not read from firmware:

  ```
  critical_temp = min(tempN_crit)            or 100 °C if absent
  max_temp      = min(tempN_max)             or critical - 10 °C if absent
  psv_temp      = max_temp + (critical_temp - max_temp) / 2
  ```

  A `PASSIVE` trip at `psv_temp` gets `rapl_controller`, `intel_pstate`,
  `intel_powerclamp`, `cpufreq`, `Processor` bound in that order (overridable via
  [data/thermal-cpu-cdev-order.xml](data/thermal-cpu-cdev-order.xml)); an
  `ACTIVE` trip at `max_temp` gets `Fan` if one exists. So the fan is asked to
  handle it first, and power limiting only kicks in above that;
* zones and trips from `thermal-conf.xml` are merged in;
* `--ignore-default-control` suppresses both the INT340X and the synthetic `cpu`
  zone, leaving *only* what the XML config says.

Finally, `sort_and_update_poll_trip()` sorts each zone's trips by temperature and
inserts a synthetic `POLLING` trip 10 % (minimum 5 °C) below the lowest real
trip. Crossing it upward switches the sensor to fast (1 s) polling; crossing it
downward resets all cooling devices in the zone to `min_state`. This is why
thermald appears to do nothing at all until you get near the first real trip, and
why cooling is released quickly once you cool down.

**If you want to know what thermald decided on a given machine, do not guess —
read the `ZONE DUMP` block in the log** (see [section 9](#9-debugging)).

## 5. The control loop

`cthd_engine::thd_engine_thread()` in [src/thd_engine.cpp](src/thd_engine.cpp):

```
for (;;) {
    poll(poll_fds, poll_fd_cnt, poll_timeout_msec);   // wakeup pipe + kobj uevent
    rapl_power_meter.rapl_measure_power();

    if (timed out || poll interval elapsed)
        for each zone: zone->zone_temperature_notification()

    if (thermal kobject uevent)     // debounced to 3 s
        for each zone: zone->zone_temperature_notification()

    if (message on wakeup pipe)
        proc_message()             // TERMINATE, PREF_CHANGED, RELOAD_ZONES,
                                   // POLL_ENABLE/DISABLE, FAST_POLL_*
    if (thd_poll_interval elapsed)
        update_engine_state();     // no-op in default engine;
                                   // re-evaluates conditions in adaptive engine
    workarounds();
}
```

Timing, and why it confuses people:

* `--poll-interval` (default **4 s**) sets both the poll timeout *and* the
  `update_engine_state()` cadence via the global `thd_poll_interval`.
* `--poll-interval 0` disables the timeout-based polling. thermald then relies on
  kobject uevents from `/devices/virtual/thermal/thermal_zone`. It will refuse to
  do so and force 4 s polling if any active zone has a sensor that is not
  async-capable. Note that with `thd_poll_interval == 0`,
  `update_engine_state()` then runs on *every* wakeup.
* `poll_timeout_sec` is captured *once* before the loop. Fast-poll changes
  `poll_timeout_msec` (to 1000 ms) but not that captured value, so the
  "interval elapsed" check keeps using the original interval. Worth knowing
  before you conclude a timing bug.
* A `thermal-conf.xml` `<PollingInterval>` overrides the command line.

The path from a wakeup to a hardware write:

```
zone_temperature_notification()
 └─ read_zone_temp()                       zone temp = max() over its sensors
     └─ thermal_zone_temp_change()
         └─ for each trip: thd_trip_point_check()
             └─ cdev->thd_cdev_set_state()
                 └─ set_curr_state() → write to sysfs
```

`SENSORS_CORELATED` zones (e.g. `cpu`) evaluate once using the hottest sensor;
`SENSOR_INDEPENDENT` zones evaluate once per sensor.

## 6. Decision making

### 6.1 Trip point evaluation

`cthd_trip_point::thd_trip_point_check()` in
[src/thd_trip_point.cpp](src/thd_trip_point.cpp). In order:

1. **Dependency check** (`DependsOn` in XML): if this trip is gated on another
   cooling device's state and the relation (`==`, `<`, `>`, `<=`, `>=`) does not
   hold, do nothing. This is how you express "only power-limit if the fan is
   already maxed out".
2. **Sensor filter**: skip if the trip is bound to a specific sensor and this is
   not it.
3. **`CRITICAL`**: power off the machine — but only after
   `consecutive_critical_events` (4) consecutive readings above the trip, and not
   at all under `--ignore-critical-trip`.
4. **`HOT`**: suspend to memory, same debounce.
5. **`POLLING`**: the synthetic trip described above; toggles fast polling and
   sets `*reset`, which makes the zone release all cooling.
6. **User preference filter**: `PREF_PERFORMANCE` only applies `ACTIVE` and `MAX`
   trips (prefer fans over throttling); `PREF_ENERGY_CONSERVE` (the **default**,
   see [src/thd_preference.cpp](src/thd_preference.cpp)) only applies `PASSIVE`
   and `MAX`; `PREF_DISABLED` applies nothing. Set over D-Bus, persisted in
   `TDRUNDIR/thd_preference.conf`.
7. **Threshold and hysteresis**: turn on at `temp >= trip`, turn off at
   `temp + hyst < trip` once on.
8. **Act on cooling devices**: on activation, walk the cdev list forward,
   skipping any already in `max_state`; on deactivation walk it backward,
   skipping any already in `min_state`. With `SEQUENTIAL` control (the default
   for the CPU zone and for adaptive-installed trips) it stops after the first
   cdev that accepted the call — so cooling devices are exhausted **in order**,
   and only when the first has nothing left to give does the second get used.
   `PARALLEL` acts on all of them. A per-cdev `sampling_period` rate-limits
   activation.

There is one deliberate exception to "skip if already in max_state": a
PID-controlled cdev with an inverted range keeps getting called at `max_state`,
so the PID can *relax* the limit as temperature falls back toward the target
instead of staying pinned until the trip fully deactivates.

### 6.2 Applying a state

`cthd_cdev::thd_cdev_set_state()` in [src/thd_cdev.cpp](src/thd_cdev.cpp) is the
most intricate function in the codebase. Read the long comment above it before
changing anything. The essentials:

* **Multiple owners.** The same cooling device is often driven by several
  trips in several zones. Every activation pushes a `{zone, trip, target}`
  record onto `zone_trip_limits`; deactivation pops it. A device is only
  actually released when that list is empty. This is why one zone cooling down
  does not undo another zone's throttling.
* **The most restrictive request wins.** The list is kept sorted (ascending or
  descending depending on range direction) so the last element is the most
  restrictive, and that is the one applied.
* **Debounce.** Repeated activations within `debounce_interval` (default 2 s)
  are ignored.
* Then one of four control strategies, in priority order:
  1. **explicit target state** — write exactly what was asked for (this is what
     DPTF PSVT/ITMT tables use);
  2. **hard target** (`MAX` trip) — go straight to `max_state`;
  3. **PID**, if configured for this trip or this cdev;
  4. **exponential controller** — the default.

### 6.3 The exponential controller

`thd_cdev_exponential_controller()`. On the first activation it moves one step
(`inc_dec_val`, or `inc_val`/`dec_val` if given). If activation is called again
consecutively — meaning the previous step did not bring the temperature under
control — the step size doubles each time (`base + 2^n * step`, capped at
`default_max_exponent = 20`). Deactivation always steps down linearly, to avoid
ping-pong. `auto_down_adjust` makes deactivation jump straight to `min_state`.

### 6.4 PID control

[src/thd_pid.cpp](src/thd_pid.cpp). Same formula in both modes,
`u = Kp*e + Ki*∫e·dt + Kd*de/dt` where `e = current_temp - target_temp`; the
difference is what the output is applied to:

* **`PID_ABSOLUTE`** (default): `new_state = min_state ± u`. Settles at a fixed
  state proportional to the error. The first call seeds `err_sum` so that the
  output equals the current state — a bumpless start.
* **`PID_INCREMENTAL`**: `new_state = curr_state ± u`. Keeps ratcheting the limit
  down every poll while the temperature stays above target, and on deactivation
  restores `min_state` and resets the PID.

The `±` is the inverted-range handling again. Configure via `<PidControl>` in
`thermal-conf.xml`, either per trip-cdev binding or per cooling device.

## 7. The adaptive engine (`--adaptive`)

`cthd_engine_adaptive` ([src/thd_engine_adaptive.cpp](src/thd_engine_adaptive.cpp))
derives from `cthd_engine_default`. It is enabled by default in
[data/thermald.service.in](data/thermald.service.in):

```
ExecStart=@sbindir@/thermald --systemd --dbus-enable --adaptive
```

so on most distributions **this is the mode your users are running**.

### 7.1 What it is for

Intel platforms ship their thermal policy inside ACPI, in a binary blob exposed
by the kernel INT3400 driver as `data_vault`. Windows' DPTF/DTT driver reads it
and implements the OEM's intended behaviour. Adaptive mode is thermald's
best-effort implementation of the same thing: parse the blob, work out which
policy applies to the current situation, and install it as thermald zones and
trips.

Practical consequence, and the thing to tell users first: **in adaptive mode
`thermal-conf.xml` is ignored entirely.** `thd_engine_init()` sets
`parser_disabled = true` and `thd_ignore_default_control = 1`, so there is no XML
config and no synthetic `cpu` zone. It also sets `force_mmio_rapl = true` and
switches to `EXCLUSIVE` control, taking the kernel's zones out of the picture.

### 7.2 The data vault

`cthd_gddv` ([src/thd_gddv.h](src/thd_gddv.h),
[src/thd_gddv.cpp](src/thd_gddv.cpp)) parses it. Source, in order:

1. a file under `/lib/firmware/intel/dtt/dtt_data_vault_<crc32 of sys_vendor>_<product_family>_<product_name>_<product_sku>.bin` — see `format_dv_filename()`; can be disabled with `<DataVaultFromFileSystem>0</DataVaultFromFileSystem>`;
2. otherwise `<int3400>/data_vault` from sysfs.

The blob is an ESIF key/value repository, sometimes LZMA-compressed and often
containing nested repositories. Tables that matter:

| Table | Purpose |
| --- | --- |
| **APCT** | condition sets — "when is this policy active" |
| **APAT** | targets — "what to do when it is active" |
| **APPC** | custom/OEM condition definitions, merged into APCT |
| **PSVT** | passive table: sensor → cooling device, trip temperature, limit |
| **ITMT** / ITMT3 | Intel Thermal Management Table: trip temperature → PL1 min/max range |
| **PPCC** | RAPL power limit capabilities (PL1/PL2 min, max, time window) |
| **IDSP** | supported policy UUIDs — gates which ITMT version may be used |
| **VSCT/VSPT** | virtual sensor definition and its polling table |
| **TRT** | ACPI thermal relationship table |

### 7.3 Conditions

`conditions` is a list of condition *sets*; a set matches only if **every**
condition in it matches (logical AND), and the first matching set wins
(`evaluate_conditions()`). Each condition names a quantity, a comparison
(`==`, `<=`, `>=`, `!=`), an argument, and optionally a dwell time — the
condition must hold continuously for that long before it counts.

thermald can evaluate only a subset of the ~80 DPTF condition types:

| Condition | Source in thermald |
| --- | --- |
| `Default` | always true |
| `Oem0`–`Oem5`, and OEM ids ≥ 0x1000 | `<int3400>/odvpN` sysfs |
| `Temperature`, `Temperature_without_hysteresis` | a thermald sensor |
| `Lid_state` | libevdev, `SW_LID` |
| `Power_source` | upower (AC vs battery) |
| `Workload` | not really implemented; matches a fixed value |
| `Platform_type` | tablet/clamshell via libevdev |
| `Power_slider` | power-profiles-daemon `ActiveProfile` over D-Bus: power-saver→25, balanced→75, performance→100 |
| `OS_type` | fixed |
| `Motion` | matches only `== 0` |

Everything else is unsupported. Two ranges are called out explicitly in
[src/thd_gddv.h](src/thd_gddv.h): OEM conditions (`0x1000`–`0x1fff`) map to
`odvpN`, while **software-OEM conditions (`0x2000`–`0xffff`) are set by OEM
software through DPTF and have no Linux equivalent**, so any set using them can
never match — by design, and logged as such rather than treated as an error.

`verify_conditions()` reports whether any unsupported condition exists;
`evaluate_conditions()` returns the matched target id or −1.

### 7.4 Targets

A matched condition set names a target id. Targets found in APAT are executed by
`execute_target()`:

* if the target's participant resolves to a cooling device, the code is handed
  to `cdev->set_adaptive_target()` — e.g. `PL1MAX`, `PL1PowerLimit` adjust RAPL
  `min_state`/`max_state`;
* if the participant is the INT3400 itself, `set_int3400_target()` handles
  `PSVT`, `ITMT`, `ITMT3` and `PSV`.

Installing a PSVT or ITMT is destructive: every existing zone is reset, has all
its trips deleted and is deactivated (except the debug-only `rapl_pkg_power` and
`power_floor` zones), and then the table's entries are installed as fresh
`PASSIVE` trips with `SEQUENTIAL` control.

* `install_passive()` — one PSV row becomes: zone = target participant's short
  name, cdev = source participant, trip temp = deci-Kelvin converted to
  millidegrees, target state = the row's `limit` (`MAX` → invalid/unclamped,
  `MIN` → 0, otherwise the number × 1000), sampling period = `sample_period / 10`.
* `install_itmt()` — one ITMT row becomes a trip on `rapl_controller_mmio` with
  a min/max PL1 range. **Note the deliberate swap** of `pl1_min`/`pl1_max` when
  calling `thd_trip_point_add_cdev()`: an ITMT row "above 45 °C set PL1 to 28 W"
  means unthrottled = `pl1_max` = thermald's `min_state`, throttled = `pl1_min` =
  thermald's `max_state`. The comment in the source explains it; do not "fix" it.

Participant name matching is fuzzy on purpose: the last dot-separated component
of the ACPI path is used, trailing underscores are stripped, and `B0D4` ↔ `TCPU`
are tried as aliases in both directions.

### 7.5 `psvt_consolidate()`

DPTF and thermald express passive control differently: DPTF rows say "at this
temperature, hold this limit", thermald trips say "above this temperature, act".
`psvt_consolidate()` bridges the two:

* a single trip with a valid target state gets a second trip 1 °C higher, so
  control can continue to `max_state` instead of stopping at the one row;
* a `MAX` target that is the last trip becomes "no explicit target,
  temperature + 1 °C";
* a `MAX` target followed by another trip on the same sensor and cdev is
  collapsed into the midpoint of the two temperatures with the midpoint state.

If you are chasing "the trips thermald installed do not look like the table",
this function is usually the answer.

### 7.6 When adaptive mode gives up

Several distinct paths, worth knowing because they look different in the log:

* **No INT3400, no `data_vault`, unreadable or unparseable blob** →
  `thd_engine_init()` returns an error → `main()` silently falls back to the
  default engine. Common on AMD and on older Intel systems, and completely
  normal.
* **Unsupported CPU model** and no `--ignore-cpuid-check` → `exit(EXIT_SUCCESS)`.
  No fallback: the daemon just stops.
* **No conditions in the blob** but an `IETM.D0` default PSVT exists →
  `passive_def_only` mode: install that table once and skip all per-poll
  condition evaluation.
* **Conditions exist but none can ever match** → `find_agressive_target()` picks
  the target with the highest PL1MAX (i.e. the least restrictive) as a fallback,
  so the machine is not left throttled by an arbitrary policy. Failing that, the
  default PSVT is installed.
* **A table was installed but produced zero active zones** (usually because the
  PSVT references sensors this kernel does not expose) → thermald creates
  `TDRUNDIR/ignore_adaptive` and calls `exit(EXIT_FAILURE)`. systemd's
  `Restart=on-failure` restarts it; adaptive init now sees `ignore_adaptive` and
  bails immediately, so the restarted daemon runs the default engine. If a user
  reports "thermald restarted once at boot and now behaves differently", this is
  why. Removing the file re-enables adaptive mode on the next start.

### 7.7 Re-evaluation

`update_engine_state()` runs every `thd_poll_interval` seconds. It re-evaluates
the conditions and, **only if the matched target changed**, tears down and
reinstalls the tables. So plugging in AC, closing the lid or switching power
profile can change the entire trip point layout within a few seconds. In
`passive_def_only` mode it returns immediately.

## 8. Command line options

From `options[]` in [src/main.cpp](src/main.cpp).

| Option | Effect |
| --- | --- |
| `--version` | print version, exit |
| `--no-daemon` | stay in foreground, log to stdout instead of syslog |
| `--systemd` | started by systemd: do not fork, but still use syslog |
| `--loglevel=info` | add `G_LOG_LEVEL_INFO`. This is a flag *name*, not a value |
| `--loglevel=debug` | add info + debug. What you want for any bug report |
| `--adaptive` | try the adaptive engine, fall back to default (see [section 7](#7-the-adaptive-engine---adaptive)) |
| `--poll-interval N` | poll every N seconds; `0` disables timed polling and also makes `update_engine_state()` run every wakeup. Default 4 |
| `--dbus-enable` | start the D-Bus server |
| `--exclusive-control` | set every thermal zone policy to `user_space` and enable the INT3400 zone; restored on clean exit |
| `--ignore-cpuid-check` | skip the CPU model allowlist |
| `--config-file PATH` | use this XML config instead of the default search order |
| `--ignore-default-control` | no INT340X zone, no synthetic `cpu` zone — only what the XML says |
| `--workaround-enabled` | every ~30 s, re-apply the RAPL MMIO workaround and clamp TCC offset to 5 if it reads above 10 |
| `--disable-active-power` | do not create the RAPL MMIO cooling device; disables active power-limit raising |
| `--ignore-critical-trip` | never power off or suspend on `CRITICAL`/`HOT` trips |
| `--power-floor-enable` | subscribe to the power floor notification and create a `power_floor` zone bound to `intel_powerclamp` (plus `PCIe_Port_Link_Speed` if present) |

Two discrepancies with [man/thermald.8](man/thermald.8) worth fixing or noting:

* `--test-mode` is documented in the man page and exists in
  [src/android_main.cpp](src/android_main.cpp), but is **not registered** in
  [src/main.cpp](src/main.cpp) — passing it to the Linux binary is an error. The
  `test_mode` variable there is always false, so the "exit instead of falling
  back" behaviour is unreachable on Linux.
* `--power-floor-enable` is implemented but undocumented in the man page.

## 9. Debugging

### Getting a useful log

```bash
sudo systemctl stop thermald
sudo thermald --no-daemon --loglevel=debug --adaptive        # or without --adaptive
```

`--no-daemon` sends output to stdout; otherwise it goes to syslog/journal. There
are ready-made collection scripts:
[test/thermal-debug-dump-fedora.sh](test/thermal-debug-dump-fedora.sh),
[test/thermal-debug-dump-ubuntu.sh](test/thermal-debug-dump-ubuntu.sh),
[test/thermal-dptf-tables-test-fedora.sh](test/thermal-dptf-tables-test-fedora.sh).

### Log lines to look for first

| Line | Tells you |
| --- | --- |
| `Using config file ...` / `Using generated ...` | which XML was picked |
| `Unsupported cpu model...` | why nothing happened |
| `PM profile is N` / `Non-mobile platform` | thermald is running somewhere its tables were never validated |
| `ZONE DUMP BEGIN` … `END` | **the authoritative answer to "what is thermald controlling?"** — every zone, its sensors, its trips and the cooling devices bound to each |
| the cdev dump (`index: type, C:.. MN:.. MX:.. ST:..`) | current/min/max state and step of every cooling device |
| `Set : threshold, temperature, cdev, curr_state, max_state` | a control action was taken |
| `Set pid(abs\|inc[,inv])` | a PID action was taken |
| `Added zone N trip M clamp...` / `Erased [..]` | the multi-owner bookkeeping in `thd_cdev_set_state()` |
| `Condition Set matched:N target:M` | which adaptive policy is active |
| `Unsupported condition N (name)` | why an adaptive policy can never match |
| `Adaptive policy couldn't create any zones` | the `ignore_adaptive` bail-out |
| `Ignore: delay < debounce interval` | an action was skipped on purpose |

### Debug mode

`touch /var/run/thermald/debug_mode` before starting. `debug_mode_on()` then adds
a `rapl_pkg_power` sensor and zone so package power can be plotted, and enables
extra condition-comparison tracing. These zones are deliberately preserved when
adaptive mode tears everything down.

### Plotting

[test/thermald_debug_output_graph.py](test/thermald_debug_output_graph.py) plots
temperatures and trips from a debug log;
[test/thermal_temp_dump.py](test/thermal_temp_dump.py) and
[test/thermal_config_dump.py](test/thermal_config_dump.py) are also useful.
`ThermalMonitor` (a separate GUI, referenced from the man page) talks over D-Bus.

### Testing without the hardware

[test/readme_test.txt](test/readme_test.txt): build
[test/thermald_test_kern_module.c](test/thermald_test_kern_module.c) against your
kernel with `CONFIG_THERMAL_EMULATION=y`, load it, then run
[test/exec_config_tests.sh](test/exec_config_tests.sh) — you get a loopback
thermal zone whose temperature you can drive via `emul_temp`.
[test/using_test_data_vault.txt](test/using_test_data_vault.txt) explains how to
feed a canned data vault into adaptive mode from
`/lib/firmware/intel/dtt/`, which is how you reproduce another machine's DPTF
tables locally. Sample data vaults are in [test/gddv_tests/](test/gddv_tests/).

## 10. Configuration files

| Path | Purpose |
| --- | --- |
| `/etc/thermald/thermal-conf.xml.auto` | preferred; user-editable copy of a generated config |
| `/var/run/thermald/thermal-conf.xml.auto` | generated at startup from the ACPI thermal relationship table |
| `/etc/thermald/thermal-conf.xml` | hand-written config |
| `/etc/thermald/thermald-features.xml` | feature kill switches, see below |
| `/etc/thermald/thermal-cpu-cdev-order.xml` | override the default CPU cooling device order |
| `/var/run/thermald/thd_preference.conf` | persisted user preference |
| `/var/run/thermald/thd_user_psv_temp.<zone>.conf`, `thd_user_set_max.<zone>.conf` | per-zone overrides set over D-Bus |
| `/var/run/thermald/ignore_adaptive` | marker that disables adaptive mode |
| `/var/run/thermald/debug_mode` | marker that enables debug extras |
| `/var/run/thermald/thermald.pid` | single-instance lock |

Search order is in `cthd_parse::parser_init()`
([src/thd_parse.cpp](src/thd_parse.cpp)): `--config-file` wins; otherwise
`/etc/thermald/thermal-conf.xml.auto`, else generate
`/var/run/thermald/thermal-conf.xml.auto` from ACPI, else
`/etc/thermald/thermal-conf.xml`. Config files are opened through
`open_validated_xml_file()` — symlinks are refused, and a DTD in the document is
rejected.

[data/thermald-features.xml](data/thermald-features.xml) can disable whole
subsystems, checked via `check_feature()`
([src/thd_features_parse.h](src/thd_features_parse.h)):
`DbusControl`, `XMLThermalConfig`, `DataVaultFromFileSystem`,
`KobjectUeventSupport`.

## 11. D-Bus interface

Bus name `org.freedesktop.thermald` on the system bus; interface defined in
[src/thd_dbus_interface.xml](src/thd_dbus_interface.xml), implemented in
[src/thd_dbus_interface.cpp](src/thd_dbus_interface.cpp), policy in
[data/org.freedesktop.thermald.conf](data/org.freedesktop.thermald.conf). Only
active with `--dbus-enable`.

Read-only introspection: `GetSensorCount`, `GetSensorInformation`,
`GetSensorTemperature`, `GetZoneCount`, `GetZoneInformation`,
`GetZoneSensorAtIndex`, `GetZoneTripAtIndex`, `GetCdevCount`,
`GetCdevInformation`, `GetCurrentPreference`, `GetZoneStatus`.

Mutating: `SetCurrentPreference`, `SetUserMaxTemperature`,
`SetUserPassiveTemperature`, `AddSensor`, `AddVirtualSensor`, `AddZonePassive`,
`DeleteZone`, `SetZoneStatus`, `AddTripPoint`, `DeleteTripPoint`,
`AddCoolingDevice`, `UpdateCoolingDevice`, `DisableCoolingDevice`, `Reinit`,
`Terminate`.

Anything reaching the engine from here is attacker-adjacent input. Existing
handlers validate names with `is_valid_thermal_object_name()`, resolve paths
with `realpath()` and require a `/sys/` prefix
(`canonicalize_sysfs_path()`), and bound numeric ranges. Match that standard in
new methods. [tools/thermald_set_pref.sh](tools/thermald_set_pref.sh) and
[test/default.sh](test/default.sh) are handy manual clients.

## 13. Contributing

Build (see [README.txt](README.txt) for the per-distro dependency lists):

```bash
./autogen.sh prefix=/     # or prefix=/usr — match your distro's existing install
make
sudo make install
```

Before sending a pull request:

* **Match the existing style.** Tabs, K&R braces, `cthd_`/`thd_` prefixes,
  `THD_SUCCESS`/`THD_ERROR`/`THD_FATAL_ERROR` return codes. Log with
  `thd_log_debug/info/msg/warn/error`, never `printf`.
* **Keep it clean under the static analysers.** [.clang-tidy](.clang-tidy) is
  configured, and the project actively tracks Coverity and clang-tidy findings.
  CI lives in [.github/workflows/](.github/workflows/).
* **Do not regress the inverted-range or multi-owner logic** in
  [src/thd_cdev.cpp](src/thd_cdev.cpp). If you change either, exercise it with
  a RAPL cooling device (max < min) driven by two zones at once.
* **Treat firmware and D-Bus data as hostile.** The data vault comes from BIOS
  and has had real bounds bugs; validate lengths, bound loops, prefer
  `std::unique_ptr` over raw `new`/`delete`, and open files with `O_NOFOLLOW`
  where a symlink would be a problem.
* **Add a test** where the loopback module makes it possible: an XML config plus
  a script under [test/](test/), wired into
  [test/exec_config_tests.sh](test/exec_config_tests.sh); or a data vault under
  [test/gddv_tests/](test/gddv_tests/) for parser changes.
* **Update the man pages** ([man/thermald.8](man/thermald.8),
  [man/thermal-conf.xml.5](man/thermal-conf.xml.5)) when you add an option or a
  config element, and add a release note to [README.txt](README.txt).
* **Include a debug log** in bug reports and in PRs that change control
  behaviour — the `ZONE DUMP` and the `Set :` lines are what reviewers will
  actually read.
